# G5 マージの門番

> 作業ブランチの変更を、最新の main と合わせた状態で検査し、すべて通れば人の操作なしで main に反映する。

## 意図

J4・J10 で、自動化の範囲はマージまでと決めた。ところが今は AI が main に直接コミットしており、検査を通さずに反映できてしまう。
main に入るのは、ゴール文書の検査・テスト・隠しシナリオ・監査をすべて通ったものだけにする。人はコードの差分を見ない（G0 の非ゴール）。

## 具体例

- E1 `[機械]` `npm run gate` の1つで、作業ブランチを最新の main と合わせた状態で、ゴール文書の検査・テスト・隠しシナリオ・監査がすべて走る
- E2 `[機械]` すべて通れば、人の操作なしで main に反映され、GitHub に push される
- E3 `[機械]` 1つでも落ちれば反映されず、落ちた理由が報告される。隠しシナリオについては、通し番号と具体例の ID だけが出る
- E4 `[機械]` 監査は、保管場所への「許可された接触」があれば落とす。拒否された試みは報告するが、落とさない
- E5 `[機械]` 実装 AI が main で直接コミットや push をしようとすると、止められる
- E6 `[機械]` 最初の実践として、G5 自身の変更を門番に通して main に反映する

## 非ゴール

- GitHub 側のブランチ保護やプルリクエスト（当面は手元の門番で行う）
- 本番への反映（J10 のとおり事前承認のまま）
- 複数の作業ブランチを順番に処理する仕組み（マージキュー）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- 作業は `work/<名前>` のブランチで行う
- 門番の流れ（main には、マージした結果で検査を通ったものだけが入る）
  1. 作業ツリーに未コミットの変更がなく、今のブランチが main でないことを確かめる
  2. 一時フォルダに main の worktree を作り、作業ブランチをマージする。作業ブランチ単体ではなく、マージした結果を検査する
  3. マージした結果の中で、ゴール文書の検査、テスト、隠しシナリオ（評価対象ごと）、監査を順に実行する
  4. すべて通れば main をマージした結果まで進め、GitHub に push する。落ちたら main は変えず、理由を報告する
  5. 一時 worktree を片づける
- 隠しシナリオは、マージした結果の側のツールで実行する。出力は件数と通し番号・具体例の ID だけなので、報告に中身は混ざらない
- main での直接のコミット・push を止める（E5）：Claude Code の PreToolUse フック（Bash）で、今のブランチが main のときの `git commit`・`git merge`・`git push` と、main への push を止める。門番は Claude Code の Bash を通さずに git を操作するので止まらない
- 監査の改善（G3.3 の未対応の1つ）
  - 作業記録で、道具の使用とその結果を突き合わせ、「許可された接触」「拒否された試み」「失敗」「結果不明」に分ける。門番は「許可」と「不明」があれば落とす
  - 保管場所の判定は、保管場所のパス（絶対パスか `~/codes/saihai-evals`）で行う。`saihai-evals-probe` のように名前が似た別のパスは拾わない
  - Bash のヒアドキュメントの本文（コミットメッセージなど）はデータなので、接触とみなさない

### 調べたこと

既存の知識に基づく。今回は新たに検索していない。

- **Not Rocket Science Rule**（Graydon Hoare）：main には、マージした結果でテストを通ったものだけを入れ、main を常に通る状態に保つ。bors や GitHub のマージキューの考え方の元
- よく知られた落とし穴：不安定なテスト、作業ブランチ単体では通るがマージ後に壊れること、門番を迂回した反映

### 既知の落とし穴

| 落とし穴 | 対策 |
|---|---|
| 作業ブランチ単体では通るが、main と合わせると壊れる | マージした結果で検査する |
| 門番を迂回して main に反映する | PreToolUse フックで止める。フックを通らない操作は止められないので、監査で検出する（後続） |
| 不安定なテストで、門番が通ったり落ちたりする | 落ちたら自動で再実行せず、理由を報告する。再実行で通すのは評価のハックになりうる |
| ヒアドキュメントの中で保管場所を読むと、監査をすり抜ける | 受け入れる。設定の Bash の禁止と自動モードの判定が先に止める（G3.3 の実験） |
