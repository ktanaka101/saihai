# G8 実装への委任

> ゴール文書から実装する AI への委任指示を作り、実装区間を AI だけで閉じる。AI が自分で決めたことは判断ログに残し、人は解釈区間でまとめて見る。

## 意図

- 目的：人が決めたゴール文書を、そのまま実装する AI への委任指示（指揮官の意図・制約・報告条件）にし、実装区間を AI だけで閉じる
- 理由：実装中に人へ同期的に問い合わせると、ボトルネックが実装区間に戻る。AI は指示に従う方向に寄りやすく、誤った制約を黙って守るか、黙って破る（G1.1 の実例、J58）
- 望ましい最終状態：実装する AI は委任指示を読み、バックブリーフを残してから着手し、報告条件以外は自分で決めて判断ログに残す。人は解釈区間で、抽出された重要な判断だけを見る

## 仮説と判定

- 仮説：委任指示と判断ログがあれば、実装中の人への問い合わせは報告条件の分だけになり、AI の判断と逸脱が後から検証できる形で残る
- 当たりの判定：判断ログが残り、逸脱や制約への指摘も記録される（観測：`判断ログの件数 >= 5`、`逸脱と指摘 >= 1`）
- 外れの判定：判断ログが残らないまま実装が進む（観測：`判断ログの件数 < 1`）

## 具体例

- E1 `[機械]` `npm run brief -- <ID>` で、そのゴールと祖先のゴールの意図・仮説・制約・報告条件をまとめた委任指示ができる
- E2 `[機械]` 委任指示には、着手前のバックブリーフ、判断ログへの記録、逸脱の報告、黙って従わないことの依頼が含まれる
- E3 `[機械]` 判断ログの各件は決まった項目（判断・関連・理由・退けた案・制約との関係・可逆性・影響範囲）を持ち、検査で確かめられる
- E4 `[機械]` `npm run log` で判断ログに1件足せ、ID は通し番号になる
- E5 `[機械]` 実装する AI 向けの指示書（CLAUDE.md）が、委任指示と判断ログの使い方を伝える
- E6 `[機械]` 最初の実践として、次のゴール（G7.1）の実装をこの委任指示で行い、判断ログを残す

## 不変条件

- 報告条件に当たったら、止まって人に聞く — 理由：実装区間で人を待たせるのは報告条件の分だけにする（G0 の報告条件、J55）
- 不変条件から逸脱する必要が生じたら、止まって報告する — 理由：不変条件は熟考して決めたもので、AI の判断で破らない（J58）

## 推奨

- 推奨・仮置きから逸脱するときは、目的との衝突と、守った場合に失うものを判断ログに書く — 理由：誤った制約の固定と、勝手な逸脱の両方を防ぐ（委任型の指示の原則5、J58）

## 仮置き

- 判断ログは `decisions/log.jsonl`（1行1件の JSON）に置く — 理由：機械で追記・検査・抽出しやすい（G8.E3）。人は抽出されたものだけを見る（G6.1）

## 非ゴール

- 実装そのもの（既存の AI に任せる。J43）
- 判断ログの抽出と事後検証（G6.1）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- 委任指示（`tools/brief.mjs`）：対象のゴールと祖先のゴールから、次を集めて Markdown にする
  - 指揮官の意図：対象のゴールの意図（目的・理由・望ましい最終状態）と、仮説と判定
  - 不変条件・推奨・仮置き：対象と祖先のもの（どのゴールのものかを付ける）。判例のうち強さが不変条件のもの（対象と祖先）も不変条件に加える
  - 報告条件：対象と祖先のもの
  - 受け入れの具体例と非ゴール
  - 進め方（AI への依頼）：バックブリーフ、判断ログ、逸脱の報告、黙って従わない、作業ブランチと門番
- 判断ログ（`decisions/log.jsonl`）の1件の形

```json
{"id": "D1", "date": "2026-10-12", "goal": "G7.1", "kind": "判断", "decision": "何を決めたか", "related": ["G7.1.E2", "J47"], "reason": "なぜ", "rejected": "他に何を検討し、なぜ選ばなかったか", "relation": "従った", "reversibility": "容易", "impact": ["データ形式"]}
```

  - kind：判断・バックブリーフ・報告・確認
    - 判断：decision・related・reason・rejected・relation・reversibility・impact が要る
    - バックブリーフ：着手前の解釈の要約（decision に書く）
    - 報告：止まって人に聞くこと（decision と reason）。確認されるまで受信箱に残る
    - 確認：人が見た判断や報告の ID を targets に書く
  - relation：従った・逸脱・仮置きの変更・指摘・該当なし（指摘は、理由のない制約や目的に合わない制約を、黙って従わずに指摘したもの）
  - reversibility：容易・困難
- 判断ログの検査は、ゴール文書の検査ツールに組み込む（ID の重複、日付、ゴールの存在、項目、選択肢、確認の対象の存在）
- 実装する AI 向けの指示書は、リポジトリの直下の `CLAUDE.md` に置く。Claude Code がセッションの開始時に読む

### 前提

確かめていない前提。確かめたら「調べたこと」に移す。

- Claude Code は、リポジトリの直下の CLAUDE.md をセッションの開始時に読み込む

### 調べたこと

- **委任型の指示設計**（利用者の文書、2026-10-12）：判断ログの項目（判断・関連・理由・退けた案・制約との関係・可逆性・影響範囲）、着手前のバックブリーフ、報告条件、逸脱の報告。AI は指示に従う方向に寄りやすいので、逸脱の報告を明示的に促す
- **委任型指揮（mission command）**：バックブリーフ（部下が理解した意図と計画を説明し返す）、規律ある主動性（意図に沿う範囲で現場が判断する）

### 既知の落とし穴（プレモーテム）

「半年後にこのゴールが失敗していたら、原因は何か」

| 落とし穴 | 根拠 | 対策 |
|---|---|---|
| AI が判断ログを書かずに進める | AI は指示がなければ記録しない | CLAUDE.md と委任指示で依頼し、件数を観測する（G8 の仮説） |
| 判断ログが多すぎて、人が読めない | 利用者の文書の注意点 | 人は抽出されたものだけを見る（G6.1）。全部を読む前提にしない |
| 判断ログが形だけになる（理由が空疎） | ― | 関連する ID を書かせ、どこにも紐づかない判断は抽出の対象にする（G6.1） |
