# G6.1 受信箱と事後検証

> 人が開くのは受信箱だけ。いま判断すべきことを5件まで優先順に並べ、ゴールごとの段階と、事後検証（何が起きるはずで、何が起きたか）の材料をまとめる。

## 判断待ち

### Q46 受信箱だけで判断できたか（G6.1 の仮説の判定）

- 推奨：次に受信箱（`npm run inbox`）を開いて判断するとき、ゴール文書や判断ログを直接読みに行かずに済んだかで判定する。それまでは保留にする。今回は人が受信箱を使う前に J37 で進めたので、判定の材料がない
- 自明な案：参謀の確かめ（E6）をもって当たりとする
- 取り消し：可能（判定は後から置き換えられる）

## 意図

- 目的：人の入り口を受信箱の1つにまとめ、人が判断すべきことだけを、根拠と推奨を添えて優先順に出す。解釈区間では、事後検証の材料を AI がそろえる
- 理由：判断待ち・報告・仮説の判定・判断ログは、別々の場所にある。人がそれぞれを読みに行くと、観測と解釈の区間がボトルネックになる（J42）。AI の判断は人より桁違いに多いので、全部を読む前提にはできない（利用者の文書、J58）
- 望ましい最終状態：人は `npm run inbox` を開くだけで、何に答えればよいか、どのゴールがどの段階にあるかが分かる。仮説の判定が出たゴールは、事後検証を経て次の判断につながる

## 仮説と判定

- 仮説：受信箱を入り口にすれば、人は他の資料を読みに行かずに判断できる
- 当たりの判定：人の判断が受信箱に上がった項目だけで済んでいる（人が見て判定する）
- 外れの判定：人が判断のために、ゴール文書や判断ログを直接読みに行っている

## 具体例

- E1 `[機械]` `npm run inbox` で、いま人が判断すべきことが5件まで、優先順（報告 → 判断待ち → 仮説の外れと矛盾 → 事後確認）に並ぶ。上がらなかった件数も示す
- E2 `[機械]` ゴールごとの段階（ゴール設定・実装・観測・解釈待ち・完了）が一覧で分かる
- E3 `[機械]` 判断ログの判断のうち、逸脱・仮置きの変更・指摘・戻しにくいもの・どの ID にも紐づかないものだけが事後確認に上がる。確認したものは上がらない
- E4 `[機械]` `npm run aar -- <ID>` で、事後検証の材料（起きるはずだったこと・起きたこと・判断ログの要点）がまとまる
- E5 `[機械]` 残っている仮置きの数が受信箱に出て、見直しを促す
- E6 `[人間]` 受信箱を開けば、何に答えればよいかが分かる（G0.E5）

## 不変条件

- 受信箱に一度に出すのは5件まで — 理由：上申が多すぎると、人が中身を読まずに承認するようになる（J45、G0 の既知の落とし穴）

## 推奨

- 止まって待っている報告を、いちばん上に出す — 理由：実装区間が人を待っているのは報告のときだけ（G8、J55）

## 非ゴール

- 観測そのもの（G7.1）
- 事後検証の「なぜ違ったか」「次にどうするか」を機械で書くこと（参謀が interpret スキルの手順で書く）

---

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- 受信箱の材料：ゴール文書（判断待ち・仮置き）、判断ログ（報告・判断・確認）、観測（仮説の判定）
- 段階の決め方
  - 議論中、または判断待ちがある：ゴール設定
  - 進行中：実装
  - 達成・中止で、仮説がない：完了
  - 達成で、仮説の判定が「当たり」「外れ」「矛盾」：事後検証（AI 層の「### 事後検証」）がなければ解釈待ち、あれば完了
  - 達成で、判定がそれ以外：観測
- 事後確認の対象：判断ログの判断のうち、relation が逸脱・仮置きの変更・指摘のもの、reversibility が困難なもの、related が空のもの。確認（kind が確認）の targets にあるものは除く
- 事後検証（AAR）の材料：起きるはずだったこと（意図の望ましい最終状態、仮説、当たり・外れの判定）、起きたこと（観測の判定と根拠、判断ログの件数と事後確認の対象）。「なぜ違ったか」「次にどうするか」は参謀が書き、ゴール文書の AI 層の「### 事後検証」に日付つきで残す

### 前提

確かめていない前提。確かめたら「調べたこと」に移す。

- 人は受信箱を、作業の区切りごとに開く

### 調べたこと

- **委任型の指示設計**（利用者の文書）：人は解釈区間でまとめて見る。判断ログは全部を読む前提にせず、逸脱・戻しにくい判断・影響の広い判断を先に見せる
- **委任型指揮の AAR（事後検証）**：何が起きるはずで、何が起きて、なぜ違い、次にどうするか

### 既知の落とし穴（プレモーテム）

「半年後にこのゴールが失敗していたら、原因は何か」

| 落とし穴 | 根拠 | 対策 |
|---|---|---|
| 受信箱が毎回いっぱいで、人が流し読みする | アラート疲れ | 5件まで（不変条件）。上がらなかった件数だけを示す |
| 事後確認が多すぎて、肝心の判断待ちが埋もれる | ― | 優先順を固定し、事後確認は最後に回す |
| 仮置きが見直されないまま残る | 利用者の文書の注意点 | 仮置きの数を受信箱に出す（E5） |

### 経緯

- 2026-10-12：J37 に基づき、Q40（受信箱の優先順）は判断待ちにせず推奨を採用した。採らなかった自明な案は「新しいものから順に並べる」（止まって待っている報告が埋もれるため）
- 2026-10-12：受信箱と事後検証の材料を使い、G2・G6・G7 の事後検証を行った（各文書の「### 事後検証」）
  - 達成したゴールに判断待ちがあるときと、仮説が「人が判定」のときは、段階を「解釈待ち」にした（ゴール設定に戻さない）
  - 仮説は人が判定するもの（観測の式がない）なので、判断待ち Q46 で人に判定を求めた。J37 の対象外（人の体験についての判定は、参謀が推奨を採用できない）
