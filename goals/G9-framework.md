# G9 他のプロジェクトへの導入

> saihai を1つのコマンド（saihai）と導入の手順（saihai init）にまとめ、どのプロジェクトでもゴール設定・観測・解釈の支援を使えるようにする。

## 意図

- 目的：saihai を、このリポジトリの外のプロジェクトでも使えるフレームワークにする
- 理由：ゴール設定・観測・解釈のボトルネック（J42）は、saihai 自身よりも、saihai で作るプロダクトの側にある。今のツールはこのリポジトリの goals/ にしか効かない
- 望ましい最終状態：どのプロジェクトでも、`saihai init` の後に、草案づくり・委任・受信箱・観測・事後検証が同じ手順で回る

## 仮説と判定

- 仮説：なし（理由：手段。効果は導入先でも G0 の仮説で測る）

## 具体例

- E1 `[機械]` `saihai <サブコマンド>` で init・new・check・brief・log・inbox・observe・aar・gate が使える。対象のプロジェクトは --root、環境変数 SAIHAI_ROOT、今のフォルダから上へたどる、の順で決まる
- E2 `[機械]` `saihai init` で、git のフォルダに G0 の雛形・decisions/・observations/・saihai.config.json・CLAUDE.md の節・スキル2つ・フックが入り、`saihai check` を通る
- E3 `[機械]` 既にある CLAUDE.md と .claude/settings.json は上書きせず、saihai の節とフックを足す。2回動かしても重複しない
- E4 `[機械]` 門番の検査と観測のコマンドは saihai.config.json で設定できる。既定の門番はゴール文書の検査だけ
- E5 `[機械]` saihai 自身のスキルと CLAUDE.md の節は、init が入れるものと同じ雛形から作られ、ずれれば検査で分かる
- E6 `[人間]` README を読めば、導入から最初のゴールを作るまでの手順が分かる
- E7 `[機械]` 最初の実践として、一時フォルダの新しいプロジェクトに導入し、草案・検査・委任指示・判断ログ・受信箱・観測まで動かす

## 不変条件

- 導入先の既存のファイルを上書きしない — 理由：利用者の設定を壊すと取り消しにくい（G0 の報告条件、E3）

## 推奨

- Node.js の標準だけで動かし、依存を足さない — 理由：導入の手間を増やさない（G9.E2）

## 仮置き

- フックとスキルからは、PATH 上の saihai か、init した saihai の絶対パスで呼ぶ — 理由：npm への公開は取り消しにくいので後で決める（J78）

## 報告条件

- 導入先の既存のファイルを書き換える必要が出たとき

## 非ゴール

- 導入先での評価の導出（G3）と隠しシナリオ（評価対象の定義が要る。別のゴールで扱う）
- npm への公開と、Claude Code のプラグインとしての配布（後で検討する）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- `bin/saihai.mjs`：サブコマンドを各ツールの `run` に振り分ける。対象のプロジェクト（ルート）を決めて、goals/・decisions/・observations/・saihai.config.json をそこから引く
- ルートの決め方：`--root` → `SAIHAI_ROOT` → 今のフォルダから上へ、`saihai.config.json` か `goals/G0-*.md` がある最初のフォルダ
- `saihai init`：雛形は `templates/` に置き、`{{saihai}}` を呼び方（PATH 上の `saihai`、なければ `node "<絶対パス>/bin/saihai.mjs"`）に置き換えて入れる
  - CLAUDE.md は `<!-- saihai:start -->` と `<!-- saihai:end -->` の間だけを書く。なければ末尾に足す
  - .claude/settings.json はフックを足すだけ（同じコマンドがあれば足さない）
- saihai 自身は `{{saihai}}` を `node bin/saihai.mjs` にして同じ雛形から作る。テストでずれを見つける（E5）
- saihai.config.json：`gate.checks`（門番の検査。名前とコマンド）、`probes`（観測のコマンド）、`hidden`（隠しシナリオの評価対象。saihai 自身だけ）

### 調べたこと

- **GitHub Spec Kit の `specify init`**：テンプレートを展開し、AI ごとのコマンドファイル（Claude なら `.claude/commands/`）を置く。スキルとして入れる選択肢もある（[Spec Kit の init の説明](https://www.mintlify.com/github/spec-kit/cli/init)、第三者による文書の写し）
- **Claude Code のプラグイン**：スキル・エージェント・フック・MCP サーバーなどを1つのフォルダにまとめて配れる。フックからは `${CLAUDE_PLUGIN_ROOT}` で同梱のスクリプトを呼べる（[プラグインの参考資料](https://code.claude.com/docs/en/plugins-reference)）。ただし、ゴール文書・判断ログ・設定はプロジェクトに置く必要があり、init は別に要る

### 既知の落とし穴（プレモーテム）

「半年後にこのゴールが失敗していたら、原因は何か」

| 落とし穴 | 根拠 | 対策 |
|---|---|---|
| init が利用者の CLAUDE.md や設定を壊す | ― | 印の間だけを書き、フックは足すだけにする（E3）。2回動かすテストを置く |
| saihai 自身のスキルと、導入先に入るスキルがずれる | 同じ文章を2か所に持つ | 同じ雛形から作り、テストでずれを見つける（E5） |
| saihai を移動・削除すると、導入先のフックが動かなくなる | 絶対パスで呼ぶ（仮置き） | init の出力と README で伝える。PATH 上の saihai があればそれを使う |
| ツールが saihai 自身のフォルダを前提にしたまま残り、導入先で saihai のゴールを読む | 今のツールは `tools/..` を既定にしている | すべてのサブコマンドにルートを渡し、一時フォルダでの実践（E7）で確かめる |
