# G3.3 隠しシナリオの保管と隔離

> 実装からは見えない評価（隠しシナリオ）を、リポジトリの外に保管する。実装側には、通ったかどうかと、関わる具体例の ID だけを伝える。

## 意図

- 目的：実装からは見えない評価（隠しシナリオ）をリポジトリの外に保管し、実装側には結果だけを伝える
- 理由：実装する AI が評価の中身を見られると、評価に合わせた実装ができてしまう（G1.1 の実例）
- 望ましい最終状態：実装はゴールの文言と意図に合わせるしかなく、隠しシナリオの中身は実装側に漏れない

## 仮説と判定

- 仮説：なし（理由：G3 の手段）

## 具体例

- E1 `[機械]` 2つの評価 AI の答えが一致したケースは、隠しシナリオとして保管場所に移される。実装側に伝わるのは、件数と、確かめる具体例の ID だけ
- E2 `[機械]` 答えが割れたケースは隠しシナリオにせず、G3.2 と同じく質問として人に届く
- E3 `[機械]` 隠しシナリオを実行すると、通った件数と、落ちたシナリオの具体例の ID だけが出る。入力や期待する結果は出ない
- E4 `[機械]` 新しいセッションの実装側で、保管場所を読もうとすると拒否される
- E5 `[機械]` 保管場所は git で管理され、隠しシナリオの追加は記録に残る
- E6 `[機械]` 実際に check-goals の隠しシナリオを作り、今の実装で実行する

## 非ゴール

- 同じ利用者アカウントでの、回避した読み取りの完全な防止（別のアカウントや別のマシンが必要になる）
- 評価の結果に基づくマージの判定（G5）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- 隠しシナリオづくりは、G3.2 の仕組み（ケースを作る AI と2つの評価 AI）を使う。2つの評価 AI が一致したケースだけを隠しシナリオにする。割れたケースは仕様が曖昧なので隠さず、質問として人に届ける
- 移す作業は AI でない決まった手順が行う。実装側の AI（このセッション）が受け取るのは、件数と具体例の ID の要約だけ
- 実行も決まった手順が行い、出力は「通った件数」と「落ちたシナリオの通し番号と具体例の ID」だけにする。落ちたら、実装側はゴールの文言と意図から原因を考える
- 読み取り禁止の設定（Q21 の推奨）

```json
{
  "permissions": {
    "deny": ["Read(~/codes/saihai-evals/**)", "Edit(~/codes/saihai-evals/**)", "Bash(*saihai-evals*)"]
  }
}
```

- この設定は、このセッションの途中で作った `.claude/settings.json` に入るため、このセッションには効かない（G1.1 のフックと同じ）。E4 は新しいセッションで確かめる
- 中身が実装側に漏れる経路をふさぐ
  - 一時作業フォルダに残るケースの写し：保管が終わったら、一時作業フォルダごと消す
  - 評価 AI の作業記録（書いたファイルの中身が残る）：保管場所に移す
  - 保管場所での git のフック（利用者のフックが中身を出力しうる）：保管場所のコミットではフックを動かさず、git の出力も捨てる
  - シナリオの名前（ケースを作る AI は中身を説明する名前を付ける）：保管場所では通し番号（h001 など）にし、元の名前は保管場所の中だけに残す
- 監査（J31）：Claude Code の作業記録を走査し、保管場所への接触（保管場所を指す Read などの道具の使用と、保管場所の名前を含む Bash）を一覧にする。本格的な監査は G5 で扱う

### 経緯

- 2026-10-12：書式 v2（G1.2・J58）にしたところ、v1 の書式で作った隠しシナリオ23件がすべて落ちた（新しい検査では、v1 の書式の文書は違反になるため）。仕様を意図して変えたので、これは正しい挙動。`npm run eval:hidden -- retire` で23件を引退させ、v2 の仕様（G1・G1.1・G1.2）から作り直した（J60）。採らなかった自明な案（Q37）は「古い隠しシナリオの期待を手で書き換える」（実装側が中身を見ることになるため採れない）

- 2026-10-12：E6 として `npm run eval:hidden -- generate check-goals` を実際に動かした
  - 隠しシナリオを23件保管した（G1.E1〜E6・E10 と書式の定義を確かめるもの）。今の実装で23件すべて通った。実装側に届いたのは、件数と具体例の ID だけだった
  - 割れが1件あり、隠さずに質問として出した（G1 の Q23）。半角の「:」の扱いで、G3.2 の評価では2つの評価 AI が一致していた点。これが、G3.2 の E3（割れを質問にする）が実際の評価で働いた最初の例になった
  - E4：設定の読み取り禁止は、予想と違ってこのセッションにも効いていた。保管場所への Write・Read と、保管場所の名前を含む Bash（`claude -p` の起動を含む）は、すべて拒否された
  - E3：`npm run eval:hidden -- run check-goals` の出力は「隠しシナリオ 23 件：通過 23 件・失敗 0 件」だけだった
  - 監査：作業記録149件から、保管場所への接触7件を見つけた。すべて、隔離を確かめるために意図して試したもの（どれも拒否された）
  - 改善点（未対応）：評価 AI の作業記録は保管場所に移すので、実装側の AI は中身を監査できない。作業記録の監査も、中身を出さずに結果だけを返す決まった手順にする必要がある。また、今の監査は試みを数えるだけで、拒否されたか成功したかを区別しない
- 2026-10-12：隔離の強さを実験した（Q21 の根拠）。読み取り禁止の設定をかけた新しいセッション（`claude -p`）で、ダミーのファイルを4通りの方法で読ませると、すべて拒否された。設定で拒否されたのは Read ツールとパスを書いた `cat`。パスを分割した `cat` と、`node -e` で文字列をつないで読む方法は、利用者の自動モードの判定が「回避の試み」として拒否した
