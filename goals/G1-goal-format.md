# G1 ゴール文書の書式

> 人は上半分（人間層）だけ読めば判断でき、AI は下半分（AI 層）から評価と実装に必要な根拠を引き出せる書式にする。

## 意図

G0 を書いて分かったのは、ゴール文書の大半は AI 向けの記録や根拠で、人が読む必要があるのは一部だけということ。
人の注意力を守るため、「今の意図と、人が確認・判断すべきもの」を人間層に、「記録・根拠・導出物」を AI 層に分ける。

## 具体例

- E1 `[機械]` すべてのゴール文書に frontmatter（id・parent・status・updated）がある
- E2 `[機械]` すべてのゴール文書に、人間層と AI 層の境界の見出しがある
- E3 `[機械]` 人間層は、判断待ちを除いて上限の行数に収まる
- E4 `[機械]` 判断待ちの各項目に、推奨・自明な案・取り消しの可否がある
- E5 `[機械]` 判断が決まると、その項目は判断待ちから消え、判例に移る
- E6 `[機械]` 判例（J）と判断待ち（Q）の ID は、リポジトリ全体で一意
- E7 `[人間]` 人間層だけを読めば、そのゴールが何を目指し、何を判断すべきか分かる
- E8 `[人間]` 小さなゴールは、要約・意図・具体例だけで書ける
- E9 `[人間]` G0 を新しい書式に移しても、情報が失われていない
- E10 `[機械]` 「達成」「中止」のゴールには、それを人が決めた判例がある

## 非ゴール

- 専用のエディタや GUI
- ゴール間の依存関係の可視化
- 複数人での同時編集

## 制約

- Markdown と YAML frontmatter だけで書く（git で差分を追え、Claude Code がそのまま読める）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 書式の定義

ファイル名は `goals/G{番号}-{英語の短い名前}.md`。

| 層 | 節 | 必須 | 内容 |
|---|---|---|---|
| ― | frontmatter | 必須 | id、parent、status（議論中・進行中・達成・中止）、version、updated。達成・中止にするのは人の判断で、その判例をゴールの中に置く（J18） |
| 人間層 | 題名と要約 | 必須 | 1行で、何を目指すか |
| 人間層 | 判断待ち | 任意 | 上申の形式に従う。なければ節ごと省く |
| 人間層 | 意図 | 必須 | なぜそれを目指すか |
| 人間層 | 原則 | 任意 | すべての下位ゴールに継承される原則。通常はルートゴール G0 だけが持つ（J16） |
| 人間層 | 具体例 | 必須 | 受け入れシナリオ。`[機械]` は自動で検証、`[人間]` は人が受け入れを確認、`[計測]` は運用中の指標で判定する |
| 人間層 | 非ゴール | 任意 | やらないこと |
| 人間層 | 制約 | 任意 | 守るべき条件。ルートゴールの制約はすべてのゴールに継承される（J16） |
| AI 層 | 設計 | 任意 | ゴールを満たす仕組み。AI が導出し、人が判例で決めた点を含む |
| AI 層 | 前提 | 任意 | 暗黙の前提を言葉にしたもの |
| AI 層 | 調べたこと・既知の落とし穴 | 任意 | 根拠と出典 |
| AI 層 | 判例 | 任意 | このゴールで決まったこと |
| AI 層 | 下位ゴール | 任意 | 分解案 |
| AI 層 | 参考 | 任意 | 出典の一覧 |

ID の規則：

- J（判例）と Q（判断待ち）は、リポジトリ全体で通し番号にする
- E（具体例）はゴールの中で通し番号にする。外から参照するときは `G1.E3` のように書く

判例の形式（ADR を軽くしたもの）：

| ID | 日付 | 判断 | 上申 | 置き換え |
|---|---|---|---|---|
| J{番号} | YYYY-MM-DD | 決まったこと | 元になった判断待ちの ID。複数なら「、」で区切る。会話の中で決まった場合は ― | 古い判例を置き換えた場合、その ID |

### 前提

- ゴール文書は Claude Code 上の AI が読み書きし（J9）、人は Claude Code Desktop・エディタ・GitHub で読む
- 人が主に読むのは、判断待ちと具体例

### 調べたこと

既存の書式を参考にした。今回は新たに検索しておらず、既存の知識に基づく。

- **ADR（Architecture Decision Record）**：状態・背景・決定・結果で決定を記録する。判例の形式の元にした
- **GitHub Spec Kit**：constitution.md と、機能ごとの spec・plan・tasks。憲法の考え方は同じだが、重さが課題とされる（G0 の既知の落とし穴を参照）
- **Kiro**：requirements・design・tasks の3ファイル。要件を EARS 記法（WHEN … THE SYSTEM SHALL …）で書く
- **Gherkin（Given/When/Then）**：具体例を機械で実行できる形にする書き方。人間層では自然文で書き、評価への変換は AI の仕事（G3）とする
- **BLUF（結論を先に書く）**：人間層の先頭に、要約と判断待ちを置く根拠

### 既知の落とし穴

| 落とし穴 | 対策 |
|---|---|
| AI 層が肥大化し、古い情報が残る | AI 層は導出物として扱い、いつでも作り直せるようにする。updated で鮮度を示す |
| 人間層に詳細が流れ込み、境界が崩れる | 行数の上限を機械で検査する（E3） |
| 判例が増えて互いに矛盾する | 古い判例を置き換えたら「置き換え」列に記録する |
| frontmatter と本文の内容がずれる | status などは frontmatter だけに書き、本文に重複させない |
