# G2 ゴール設定の支援

> 人の一言の意図から、参謀が下調べとプレモーテムを済ませた、G1 の書式のゴール文書の草案を作る。人は判断待ちに答えるだけでよい。

## 意図

ゴール設定は、ソフトウェアづくりの最初のボトルネック（J42）。これまでは、この会話の中で AI が手作業で下調べ・草案・上申をしてきた。
その手順を、繰り返し使える形にする。AI による要件の聞き取りは、根拠のない数字や使えない前提を作りやすく、人はそれを過信しやすい。だから草案では、確かめた事実と確かめていない前提を分けて示す。

## 具体例

- E1 `[人間]` 一言の意図から、下調べ（先行事例・既知の落とし穴・前提）とプレモーテムを添えた、G1 の書式のゴール文書の草案ができる
- E2 `[機械]` 草案の雛形は1つのコマンドで作れ、そのままゴール文書の検査を通る
- E3 `[機械]` 判断待ちは1つの文書に5件まで（G1.E11）
- E4 `[人間]` 草案では、確かめた事実（出典つき）と、確かめていない前提が分けて書かれている
- E5 `[人間]` 判断待ちがなくなったゴールは、評価（G3）と実装に進める状態になっている
- E6 `[機械]` 最初の実践として、G7（現実からの観測）と G6（解釈と次の判断）の草案をこの手順で作り、検査を通す

## 非ゴール

- 事業や戦略レベルのゴールを AI が決めること（G0 の非ゴール）
- 専用の対話画面（当面は Claude Code の中で行う。J9）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- 参謀の手順は、Claude Code のプロジェクトスキル `.claude/skills/goal-draft/SKILL.md` に書く。スキルが手順書、`npm run goal:new` が雛形づくり、`npm run check` が書式の検査を受け持つ
- 手順（Example Mapping の「ルール・具体例・問い」に対応させる）
  1. 意図を一文にする。足りない情報は推測で埋めず、判断待ちにする
  2. 下調べ：先行事例・既知の落とし穴・前提を調べる。数字や事実には出典を付け、確かめていないものは「前提」に分ける
  3. プレモーテム：「半年後にこのゴールが失敗していたら、原因は何か」
  4. `npm run goal:new` で雛形を作り、意図・具体例（`[機械]`・`[人間]`・`[計測]`）・非ゴールを埋める
  5. 決まっていないことを判断待ちにする（5件まで。推奨・自明な案・取り消し）
  6. `npm run check` を通す
  7. 判断待ちを人に上申する（J37 の間は推奨を採用し、事後通知する）。決まったものは判例に移す
  8. 作業ブランチにコミットし、門番（`npm run gate`）を通して反映する
- 判断待ちがなくなったゴールは、Example Mapping の「赤いカードがない」状態にあたる。評価（G3）に進める

### 調べたこと

- **Example Mapping**（Matt Wynne、2015）：ストーリー（黄）・ルール（青）・具体例（緑）・問い（赤）のカードで、着手前に範囲をはっきりさせる。問いのカードが残っていなければ、ストーリーはよく理解されていて着手できる。具体例は後で BDD のシナリオになる
- **LLM による要件の聞き取りの落とし穴**
  - 聞き取りを自動化した研究（LLMREI）で、根拠のない金額を作り出すなどの誤りが報告されている
  - 産業界の研究では、使えない連携やデータを前提にした、もっともらしいが現実に合わない提案が報告されている。出力は最終結果ではなく、反復の入力として扱うよう勧めている
  - 人は AI の出力を過信しやすい（自動化バイアス）

### 既知の落とし穴

| 落とし穴 | 対策 |
|---|---|
| 根拠のない数字や事実を、草案に書いてしまう | 数字と事実には出典を付ける。出典がないものは「前提」に分ける（E4） |
| 使えない連携・データ・道具を前提にする | 前提の節に書き出し、判断待ちか下調べの対象にする |
| 人が草案を読まずに承認する（自動化バイアス） | 判断待ちを5件までに絞り、推奨には理由を付ける。人間層を短く保つ（J17） |
| 意図の不足を AI が推測で埋める | 推測で埋めず、判断待ちにする |
