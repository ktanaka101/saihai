# G7 現実からの観測

> 現実（利用の記録・指標・失敗・人の判断）を集め、どのゴールのどの具体例に関わるかが分かる形でまとめる。最初は saihai 自身を観測する。

## 意図

現実からの観測は、ゴール設定と並ぶボトルネック（J42）。作ったものが現実でどう働いたかが分からなければ、次の判断ができない。
ただし、集めやすい数値を集めるだけでは、見栄えのよい数値（vanity metrics）が並ぶだけになる。観測は、ゴールの具体例から上へたどれるものだけを集める（GQM）。

## 具体例

- E1 `[機械]` `npm run observe` の1つで観測が集まり、G0 の `[計測]` の具体例と、注意力の指標に結びつけた報告ができる
- E2 `[機械]` 報告のどの数値にも、出どころ（ゴール文書・git・評価の結果・作業記録）と、関わるゴールの具体例の ID が付いている
- E3 `[機械]` 注意力の指標として、ゴールごとの判断の件数を「人が答えたもの」と「推奨を採用したもの」に分けて出す
- E4 `[機械]` 会話の作業記録からは件数だけを取り、内容は取らない
- E5 `[人間]` 報告は、人が1分で読める長さにまとまっている

## 非ゴール

- 外部のプロダクトの利用データの観測（saihai で作ったプロダクトが使われ始めたら、別のゴールで扱う）
- 観測したデータの外部への送信
- 観測の解釈と次の判断（G6）

## AI 層

> ここから下は AI 向けの記録と根拠。人は根拠を確かめたいときだけ読めばよい。

### 設計

- GQM の木に対応させる。目的（Goal）は G0 と各ゴールの意図、問い（Question）は具体例、指標（Metric）は観測の数値
- 最初の観測の対象は saihai 自身（ドッグフーディング）
  - ゴール文書：ゴールの状態、判例の件数（人が答えたもの・推奨を採用したもの（J37）・会話の中で決まったもの）、判断待ちの件数
  - git：ゴールの文書ができてから達成までの日数、門番を通った回数
  - 評価の結果：隠しシナリオの件数と通過・失敗
  - 作業記録：人の発言の件数（内容は取らない）
- 報告は「指標・値・出どころ・関わる具体例」の表にし、20行程度に収める

### 前提

確かめていない前提。確かめたら「調べたこと」に移す。

- Claude Code の作業記録から、人の発言と AI の発言を区別して数えられる
- 判例の表の「判断」列の「推奨を採用（J37）」の文字から、人が答えたものと推奨を採用したものを区別できる

### 調べたこと

- **GQM（Goal-Question-Metric、Basili ら）**：目的・問い・指標を上から順に決める。どの指標も問いと目的にさかのぼれるので、集める指標が最小限になり、集めたデータが役に立つ。元の GQM は、事業の目的やゴール同士の依存とのつながりを明示しない（GQM+Strategies で拡張されている）
- **見栄えのよい指標と、判断を変える指標**（Lean Startup）：総数のような見栄えのよい指標は、行動を変えない。判断を変える指標を使う

### 既知の落とし穴（プレモーテム）

「半年後にこのゴールが失敗していたら、原因は何か」

| 落とし穴 | 根拠 | 対策 |
|---|---|---|
| 集めやすい数値を並べただけの、見栄えのよい報告になる | Lean Startup の vanity metrics | どの数値にも関わる具体例の ID を付け、付けられない数値は集めない（E2） |
| 数値そのものが目標になる | グッドハートの法則（G0 の既知の落とし穴） | 観測は判断の材料にとどめ、合否の基準にしない。合否は具体例で決める |
| 会話の内容まで集めて、扱いに困る情報が増える | ― | 件数だけを取る（E4） |
| 件数が少なすぎて、偶然の揺れを傾向と読み違える | ― | 件数を必ず併記し、少ないときの扱いは G6 で決める |

### 経緯

- 2026-10-12：`tools/observe.mjs`（`npm run observe`）を作り、saihai 自身を初めて観測した。報告は10指標・16行で、どの数値にも出どころと具体例の ID が付いた
  - 前提だった2点（作業記録で人の発言を区別できる、判例の文字から推奨の採用を区別できる）は確かめられた。人の発言は、作業記録の発言の出どころ（human）で区別できる
  - 観測そのものの限界が2つ見つかった（G6 で解釈する）
    - 「文書ができてから達成まで」の中央値が0.0時間だった。多くのゴールで、文書を作るコミットと達成にするコミットが同じだったため、git の履歴からは期間を測れていない
    - 「人の発言」は、このセッションが一時フォルダで始まった頃の発言を数えていない可能性がある（作業記録がプロジェクトごとに分かれるため）
- 2026-10-12：G2 の手順（参謀のスキル）で草案を作った（G2.E6）。J37 に基づき、判断待ちにせず推奨を採用した。採らなかった自明な案は次のとおり。Q30（最初の観測の対象）は「外部のプロダクトの利用データ（まだない）」。Q31（作業記録から取るもの）は「内容も要約して取る」
