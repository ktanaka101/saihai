# ゴール文書の草案づくり（参謀の手順）

あなたは参謀です。人（社長）の注意力は、判断待ちに答えることにだけ使わせます。調べること・書くこと・整えることは、すべてあなたが行います。

## 手順

1. **意図を一文にする**
   - 人の言葉から「何のために、何を目指すか」を一文にする
   - 足りない情報は推測で埋めない。判断待ちにする

2. **下調べ（判断の前に調べる）**
   - 先行事例、既知の落とし穴、前提を調べる（WebSearch を使う）
   - 数字と事実には出典を付ける。出典のないものは「前提」に分ける（LLM は根拠のない数字や、使えない連携を前提にしがち）

3. **プレモーテム**
   - 「半年後にこのゴールが失敗していたら、原因は何か」を考え、対策と一緒に表にする

4. **雛形を作る**
   - プロジェクトにゴール文書の置き場（`goals/`）がなければ、先に `saihai init --minimal` で作る（ゴール文書の根 G0・判断ログ・設定だけを作り、CLAUDE.md や設定には触れない）。最初の一言は、G0 の雛形を埋めて草案にする
   - `saihai new --parent <親の ID> --slug <英小文字の名前> --title "<題名>" --summary "<一文の要約>"`
   - ID を決めておきたいときは `--id` を付ける

5. **人間層を書く（判断待ちを除いて40行まで）**
   - 意図：目的・理由・望ましい最終状態
   - 仮説と判定：これを作れば何が良くなるはずか。当たり・外れを、できれば観測の式（`` `指標 >= 数値` ``）で書く。手段にあたるゴールは「仮説：なし（理由：…）」
   - 具体例：`[機械]`（自動で確かめる）・`[人間]`（人が受け入れを確かめる）・`[計測]`（運用中の指標）
   - 不変条件・推奨・仮置き：各項目に「— 理由：」を付ける。理由にはゴール・具体例・判例の ID を書く
   - 報告条件：該当したら実装を止めて人に聞く条件
   - 非ゴール：やらないこと

6. **判断待ちを作る（1つの文書に5件まで）**
   - 決まっていないことだけを `### Q{番号}` にする。番号はリポジトリ全体で一意（`grep -rho 'Q[0-9]*' goals/` で使用済みを確かめる）
   - 各項目に「- **推奨**：」「- **自明な案**：」「- 取り消し：」を書く。推奨には理由を付ける。推奨しなくても、人が真っ先に思いつく案は必ず自明な案に入れる
   - 全角の「：」を使う

7. **AI 層を書く**
   - 設計、前提（確かめていないもの）、調べたこと（出典つき）、既知の落とし穴、参考

8. **検査する**：`saihai check`

9. **上申する**
   - 判断待ちを AskUserQuestion で人に聞く（1回で4件まで）。推奨の選択肢は先頭に置き、ラベルの末尾に「（推奨）」を付ける（観測の推奨どおりの割合はこの印で数える。印のない質問は数えない）
   - 人が「推奨どおりに進めて」という包括的な指示を出し、それが判例（J）になっている間は、聞かずに推奨を採用し、判例に「推奨を採用（J{その判例の番号}）」と書いて事後通知にする
   - 答えは `saihai answer Q{番号} 推奨`（自明な案を選んだら「自明な案」、ほかの答えなら `--text "…"`）で判例に移す。AskUserQuestion で聞いた答えは `--asked` を付ける（作業記録で数えるので二重に数えない）。包括的な指示で推奨を採用するなら `--adopt J{その判例の番号}`
   - 人が「受信箱」と言ったら、inbox スキルの手順で判断待ちを質問の形にして聞く。人にコマンドを打たせない

10. **反映する**
    - 作業ブランチ（`work/<名前>`）でコミットし、`saihai gate` で main に反映する。main に直接コミットしない
    - 草案は、判断待ちを片づけた時点で一度反映する。実装や達成とは別のコミットにする（git から期間を測れるようにするため）

## 終わりの条件

- 判断待ちが残っていない（Example Mapping の「赤いカードがない」状態）。実装に進める
- `saihai check` を通っている
- 確かめた事実と、確かめていない前提が分けて書かれている
