# ゴール文書の草案づくり（参謀の手順）

あなたは参謀です。社長（人間）の注意力は、判断待ちに答えることにだけ使わせます。調べること・書くこと・整えることは、すべてあなたが行います。

## 手順

1. **意図を一文にする**
   - 人の言葉から「何のために、何を目指すか」を一文にする
   - 足りない情報は推測で埋めない。判断待ちにする

2. **下調べ（G0 原則8：判断の前に調べる）**
   - 先行事例、既知の落とし穴、前提を調べる（WebSearch を使う）
   - 数字と事実には出典を付ける。出典のないものは「前提」に分ける（LLM は根拠のない数字や、使えない連携を前提にしがち）

3. **プレモーテム**
   - 「半年後にこのゴールが失敗していたら、原因は何か」を考え、対策と一緒に表にする

4. **雛形を作る**
   - `npm run goal:new -- --parent <親の ID> --slug <英小文字の名前> --title "<題名>" --summary "<一文の要約>"`
   - ID を決めておきたいときは `--id` を付ける（G0 の下位ゴールの一覧にある予定の ID など）

5. **人間層を書く（40行まで。J17）**
   - 意図：なぜ目指すか
   - 具体例：`[機械]`（自動で確かめる）・`[人間]`（人が受け入れを確かめる）・`[計測]`（運用中の指標）
   - 非ゴール：やらないこと

6. **判断待ちを作る（5件まで。J45）**
   - 決まっていないことだけを `### Q{番号}` にする。番号はリポジトリ全体で一意（`grep -rho 'Q[0-9]*' goals/` で使用済みを確かめる）
   - 各項目に「- **推奨**：」「- **自明な案**：」「- 取り消し：」を書く。推奨には理由を付ける。推奨しなくても、人が真っ先に思いつく案は必ず自明な案に入れる
   - 全角の「：」を使う（J34）

7. **AI 層を書く**
   - 設計、前提（確かめていないもの）、調べたこと（出典つき）、既知の落とし穴、参考

8. **検査する**：`npm run check`

9. **上申する**
   - 判断待ちを AskUserQuestion で人に聞く（1回で5件まで）
   - J37（推奨どおりに進める包括的な指示）が有効な間は、聞かずに推奨を採用し、判例に「推奨を採用（J37）」と書いて事後通知にする
   - 決まったものは判断待ちから消し、AI 層の判例の表に移す（上申列に Q の ID）

10. **反映する**
    - 作業ブランチ（`work/<名前>`）でコミットし、`npm run gate` で main に反映する
    - 草案は、判断待ちを片づけた時点で一度反映する。実装や達成とは別のコミットにする（J56。git から期間を測れるようにするため）
    - main に直接コミットしない（J39）

## 終わりの条件

- 判断待ちが残っていない（Example Mapping の「赤いカードがない」状態）。評価（G3）と実装に進める
- `npm run check` を通っている
- 確かめた事実と、確かめていない前提が分けて書かれている
